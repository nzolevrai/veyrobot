# Revue architecture, charge et fiabilité — 14 octobre 2026

## Périmètre et inventaire

Versions inspectées : Node 24.21.0, discord.js 14.27.0, BullMQ 6.3.14, Fastify 5.5, Next.js 16.4, Prisma 7.10, PostgreSQL 17.11 et Redis 7.4.11. Les mesures ont eu lieu sur Windows 10.0.26300, Intel Core i5-1135G7 (8 CPU logiques), 16,9 Go de RAM visible, avec PostgreSQL/Redis locaux dans Docker. Aucun appel Discord réel ni Gateway connecté durant cette revue.

| Niveau | Constat initial, preuve | Conséquence et changement |
|---|---|---|
| Critique | La session Fastify signée survivait à la déconnexion si une copie du cookie existait (`apps/api/src/index.ts`, ancien logout). | Ajout de `SessionGrant` haché en PostgreSQL, révocation à la déconnexion et contrôle à chaque requête authentifiée. Le test API rejoue l'ancien cookie avant et après redémarrage. Coût : une lecture SQL/session/requête. |
| Élevé | Deux processus bot avec le même token pouvaient démarrer sans coordination (`apps/bot/src/index.ts`). | Verrou advisory PostgreSQL détenu pendant la vie du bot, refus du second démarrage, test PostgreSQL réel. Ce verrou n'est pas une architecture multi-shard. |
| Élevé | Une admission sans plafond pouvait grossir indéfiniment la file durable. | Plafonds transactionnels 5 000 demandes actives globales, 100/serveur par défaut, refus 429 explicite. Un verrou global assure la décision sous concurrence, avec coût p95 mesuré ci-dessous. |
| Élevé | `Queue.add` attendait Redis sans borne même avec un producteur sans file hors ligne ; panne reproduite avec connexion refusée. | Le dispatcher vérifie l'état de la connexion avant publication ; les demandes restent `requested` en PostgreSQL. Gestionnaires d'erreur sur Queue/Worker. Le test avec double couvre l'état du producteur ; un second essai coupe un conteneur Redis éphémère et vérifie la republication après reconnexion. |
| Moyen | Sync Gateway créait une nouvelle copie du tableau de guildes à chaque ajout, donc travail quadratique (`apps/bot/src/index.ts`). | `push` dans les groupes par shard, libération après sync et arrêt du timer de reprise. Banc synthétique 20 000 guildes : 96,8–120,6 ms avant, 1,85–2,06 ms après, soit uniquement ce regroupement. |
| Moyen | Deux requêtes OAuth `guilds` simultanées de la même session déclenchaient deux appels Discord. | Coalescence des lectures concurrentes, cache borné 1 000 sessions/10 s et 1 000 chargements simultanés, refus 503 au-delà, isolation par session. Test : 50 lectures simultanées, un chargement. |
| Moyen | Le même `operationId` pouvait être rejoué avec d'autres options, et deux créations BAN concurrentes pouvaient modifier la génération. | Comparaison de toutes les options, transaction et conflit unique traité. Tests PostgreSQL de doublon et génération. |
| Moyen | Les réponses de dossiers récents pouvaient arriver hors ordre après navigation. | Annulation de l'ancienne requête et omission des réponses obsolètes dans le provider dashboard. Pas de preuve de réduction des rerenders globaux. |
| Élevé | La réécriture Next `/api` fixait `API_INTERNAL_URL` au build (`apps/dashboard/next.config.ts`) ; le test avec API sur port dynamique recevait 500 à la déconnexion. | Route serveur `/api/[...path]` qui lit la destination au runtime, relaie le cookie brut et la réponse, limite les corps à 1 MiB. Le parcours OAuth/déconnexion via Next passe après rebuild. |
| Moyen | La table d'audit, les sessions révoquées/expirées et les avertissements terminés grossissaient sans entretien. | Nettoyage manuel/configurable par lots bornés ; cas d'action et échéances conservés. Test PostgreSQL du périmètre de suppression. |

Au départ, `apps/api/src/index.ts` assemblait OAuth, session, droits, configuration et routes ; `apps/bot/src/index.ts` assemblait commandes, Gateway, dispatch, worker et cycle de vie. Après changement, l'API compose des plugins `oauth-routes`, `guild-routes`, `moderation-routes` et un contexte partagé. Le bot compose `commands`, `interactions`, `dispatcher`, `worker` et `single-instance`. `packages/db` garde Prisma, admission et rétention ; `packages/moderation` garde règles et exécution Discord ; `packages/contracts` garde les contrats de navigateur. Le domaine de modération et son adaptateur Discord restent encore réunis dans `packages/moderation/src/index.ts` : frontière à extraire avant une forte croissance de modules. Le dashboard garde son layout partagé et ses vues actuelles ; le contexte global peut toujours entraîner des rerenders étendus.

Le contrôle `tools/check-boundaries.mjs` échoue sur des imports interdits entre applications, un import serveur depuis un composant client et les cycles locaux. Il ne prouve pas à lui seul l'absence de couplage indirect, d'effets de bord ou de dépendances dynamiques.

## Mesures locales et décisions de performance

Scripts reproductibles : `packages/db/tools/benchmark.ts` (SQL seul), `packages/db/tools/explain-dispatch.sql` (base jetable, transaction annulée), `apps/bot/tools/bench-membership.mjs`, `bench-guild-cache.mjs`, `bench-pipeline.mjs`, `fault-redis.mjs` et `apps/api/tools/bench-api.mjs`, `fault-postgres.mjs`. Pour le pipeline, définir `DATABASE_URL` vers une base **isolée nommée `veyrobot_arch_bench`**, `REDIS_URL` vers la DB Redis `/9`, puis `BENCH_OFFERED_RPS=40`, `BENCH_SECONDS=4`, `BENCH_GUILDS=10` et lancer `node apps/bot/tools/bench-pipeline.mjs`. Le script rejette d'autres cibles et nettoie ses données. Il envoie à rythme fixé des créations PostgreSQL, passe par le vrai dispatcher/BullMQ et un Worker de banc simplifié qui appelle un HTTP local de 10 ms. Il mesure admission, file, traitement et bout en bout séparément, mais **n'exécute pas** le service Discord complet ni le Gateway.

Avant les changements critiques, trois essais SQL de 6 000 événements, concurrence 16/pool 10 : 904–1 066 transitions/s et p95 SQL 20,25–30,27 ms. L'ancien résultat de 60 000 dans `PERFORMANCE-BASELINE.md` reste un autre profil, pas une capacité du bot. Le regroupement Gateway synthétique est le seul gain CPU net isolé ici.

API après changement : `node apps/api/tools/bench-api.mjs`, OAuth et Discord REST simulés, PostgreSQL isolé, 10 arrivées/s pendant 5 s, trois essais de 50/50 acceptées, p95 HTTP `/guilds` 8,91/9,50/9,62 ms. À 20/s pendant 5 s, 88/100 acceptées et 12 réponses 429 à chaque essai : limite API de 90/minute après les requêtes OAuth. Ce banc mesure la réponse Fastify avec lecture de session SQL ; il n'évalue ni Discord réel ni un avant/après de latence API. Le test de coalescence prouve séparément 50 lectures concurrentes pour un seul chargement. Dashboard : build Next de 17 fichiers JavaScript statiques, 772 234 octets au total (ce total n'est pas le bundle transféré pour une route). Sur trois essais de 20 rechargements séquentiels de `/dashboard/user/profil` avec API simulée, p95 réponse serveur 12,38/12,56/12,96 ms ; aucun rendu navigateur, rerender React ou profil réseau n'a été mesuré. Une exécution intermédiaire a duré anormalement longtemps et perdu le heartbeat de test de 90 s ; le fixture renouvelle maintenant ce heartbeat avant l'assertion. Ces mesures courtes ne sont pas des garanties d'expérience utilisateur.

Pipeline initial à 40 demandes/s pendant 6 s, 10 guildes, 240/240 achevées sur trois essais : p95 bout en bout 137–2 507 ms, p95 file 65–1 930 ms. Cette variance interdit de revendiquer une amélioration globale. `Queue.addBulk` a été essayé puis écarté : trois paires alternées à 40/s étaient mixtes et deux paires à 80/s donnaient p95 ~273/263 ms séquentiel contre ~303/298 ms groupé. Le code de production garde la publication séquentielle. Sur deux premiers essais appariés à 40/s pendant 4 s, p95 admission avec borne 125/138 ms contre 8/34 ms sans la borne ; sur deux paires après échauffement et nettoyage des anciennes fixtures, 16/18 ms avec borne contre 4/4 ms sans elle. Le verrou ajoute du coût, mais les valeurs initiales étaient sensibles au bruit ; aucun gain bout en bout stable n'est revendiqué. Trois essais propres après changement à 40/s ont achevé 160/160 chacun avec p95 bout en bout 101/125/128 ms, le premier essai du lot ayant été écarté car quatre anciennes demandes ont été reprises ; le banc refuse désormais de démarrer si une demande active préexistante demeure. À 80/s pendant 4 s, 320/320 achevées, p95 admission 153 ms, file 309 ms, bout en bout 488 ms, CPU utilisateur 2,78 s, CPU système 1,06 s, RSS 206 Mo, heap 85 Mo, mémoire externe 12 Mo, event loop p95 12,44 ms et 10 connexions PostgreSQL observées. Un essai court sur une machine partagée n'est pas un débit soutenable garanti.

Objets discord.js construits hors Gateway pour 300 guildes synthétiques : environ 4,2 Ko de heap/guilde sans salon/rôle, 18,6 Ko avec 10/10 et 67,0 Ko avec 50 salons/30 rôles. Ce sont des différences de heap d'objets artificiels, sans membres, messages, shards, compression Gateway ni distribution réelle. Les caches n'ont donc pas été désactivés. L'intent actuel `Guilds` suffit aux parcours présents, les membres et bans sont lus à la demande. Une réduction de cache devra mesurer le surcoût REST.

`EXPLAIN (ANALYZE, BUFFERS)` sur 10 000 dossiers synthétiques dans une transaction annulée : le choix équitable du dispatcher a lu séquentiellement les 10 000 lignes et pris 4,657 ms ; l'échéance TEMPBAN a utilisé l'index existant et pris 0,068 ms. L'index de rétention `ConfigAudit(createdAt)` a servi à la recherche dans cet échantillon, 0,075 ms. Ce plan dépend de la sélectivité (19 % `requested` dans la fixture) ; sur une base plus volumineuse avec peu de demandes, PostgreSQL peut choisir l'index. L'index ajouté augmente le coût des écritures d'audit ; aucun gain de production n'a été affirmé.

## Invariants, pannes et exploitation

L'admission et l'écriture `requested` sont atomiques en PostgreSQL. Redis est une notification récupérable ; un job perdu est republié. Le claim `requested → running` est conditionnel, avec bail et jeton de fencing pour les écritures internes. L'appel Discord n'est pas transactionnel : un ancien exécuteur peut avoir déjà envoyé la requête avant de perdre son bail. Une réponse réseau, 5xx ou interruption après démarrage de la mutation devient `uncertain` et ne se rejoue pas automatiquement. Les tests avec doubles vérifient doublons, 403/permissions, réponse ambiguë, fencing, échéance dépassée et redémarrage ; le verrou et la rétention ont été testés avec PostgreSQL réel. Les essais de coupure Redis et PostgreSQL utilisent chacun un conteneur éphémère distinct. Aucun essai de sanction Discord réelle n'a été fait. Les pannes pendant un appel Discord, longues campagnes et 429 réels restent à éprouver.

Liveness API : `GET /health`. Readiness PostgreSQL : `GET /ready`, réponse 503 si indisponible ; cet endpoint ne teste pas la disponibilité Gateway ou Redis du bot. `node apps/api/tools/fault-postgres.mjs` a coupé puis recréé un PostgreSQL 17 éphémère distinct : readiness 200 → 503 → 200, liveness restée 200. Ce test ne prouve pas le comportement d'une sanction lorsque SQL tombe après l'appel Discord. `node apps/bot/tools/fault-redis.mjs` a coupé puis recréé un Redis 7 éphémère distinct : la demande est restée `requested` en PostgreSQL et a été republiée après reconnexion, sans exécution Discord. Une réponse 429 d'admission indique de réessayer avec le même `operationId` après désengorgement ; une opération déjà acceptée conserve son résultat antérieur. Sur incident, inspecter d'abord les dossiers `requested`, `running`, `uncertain`, les échéances `scheduled`, puis Redis et la présence des shards. Ne pas relancer manuellement une mutation `uncertain` sans vérification Discord. Les logs évitent les tokens ; il manque encore un jeu de métriques d'exploitation à faible cardinalité et des traces corrélées systématiques.

Rétention : `corepack pnpm --filter @veyrobot/db maintenance:retention` sur une base sauvegardée, avec `RETENTION_SESSION_DAYS=30`, `RETENTION_AUDIT_DAYS=730`, `RETENTION_WARNING_DAYS=1095`, `RETENTION_BATCH_SIZE=100`, `RETENTION_MAX_BATCHES=10` par défaut. Une invocation supprime au plus 1 000 lignes de chaque catégorie par défaut. Planifier hors chemin de requête et surveiller les compteurs retournés ; confirmer les délais avec les besoins légaux et de support avant production. Les dossiers d'action, `operationId`, états incertains, bans temporaires et décisions de génération ne sont jamais supprimés par cette tâche : leur croissance reste à traiter avec une politique de tombstones prouvant la conservation de l'idempotence. PostgreSQL doit être sauvegardé et une restauration doit être essayée dans une base isolée. Les migrations ajoutées sont additives ; un retour à l'ancien binaire ne retire pas leurs colonnes/index et n'est pas une stratégie de rollback d'une migration destructive.

## Montée en charge et limites prioritaires

1. **Un processus bot** : verrou de démarrage activé. Observer p95/p99 bout en bout, âge et profondeur des demandes, CPU/ELU, RSS/heap par taille de guild, pool PostgreSQL, taux 429 REST, Identify/reconnect et proportion `uncertain`. Réviser l'admission quand son p95 devient significatif ; ne pas augmenter la concurrence par serveur sans preuve d'indépendance.
2. **Plusieurs shards/processus sur une machine**, seulement après protocole de propriété des shards, routage des interactions et des tâches au propriétaire, orchestration Identify depuis `Get Gateway Bot`, reprise et arrêt progressif. Le verrou actuel empêche volontairement ce palier. Faire un essai de panne et mesurer la coordination REST avant activation.
3. **Plusieurs machines**, seulement si la mémoire/CPU, les connexions ou l'indisponibilité d'une machine le justifient par mesures longues. Évaluer propriétaire central REST (coordination simple, point de panne), proxy compatible Discord (coordination partagée, latence et exploitation supplémentaires) et coordination distribuée (meilleure répartition, forte complexité). L'API réalise aussi un GET d'installation avec le token bot : elle doit entrer dans le budget commun. Ne coder aucun limiteur à constantes fixes ; utiliser les en-têtes Discord et `Retry-After`.

Limites classées : **P1** pannes pendant l'exécution Discord, restauration PostgreSQL essayée, charge prolongée, cas `uncertain` avec observation Discord ; **P1** métriques corrélées sans cardinalité par serveur/utilisateur et budget des pools de tous les processus ; **P1** croissance des dossiers d'action et famine possible des échéances moins prioritaires ; **P2** séparation métier/adaptateur Discord et extraction du contexte global dashboard ; **P2** mesure navigateur desktop/mobile, API sous charge OAuth réelle, profils CPU Node et Gateway sur des guildes représentatives ; **P3** architecture multi-shard et coordination REST, uniquement après signaux mesurés.

## Sources et compromis (consultées le 14 octobre 2026)

- [Discord Gateway](https://docs.discord.com/developers/events/gateway) : les limites Identify et le nombre conseillé de shards viennent de `Get Gateway Bot`, avec Resume/reconnexion à distinguer ; on garde un processus tant que le routage n'est pas prêt.
- [Discord REST rate limits](https://docs.discord.com/developers/topics/rate-limits) : buckets et `Retry-After` déterminés par la réponse ; pas de plafond codé en dur. Le partage du token entre API et bot est un risque futur de coordination.
- [discord.js 14.27.0](https://discord.js.org/docs/packages/discord.js/14.27.0) : client et cache actuels, sans désactivation générale avant mesure des appels REST.
- [BullMQ production](https://docs.bullmq.io/guide/going-to-production), [idempotent jobs](https://docs.bullmq.io/patterns/idempotent-jobs), [priorités](https://docs.bullmq.io/guide/jobs/prioritized) : Redis `noeviction`, connexion bloquante du Worker sans limite de retries, identifiants stables, nettoyage des jobs ; PostgreSQL reste la preuve métier. Les priorités 1/10/20 peuvent affamer les tâches secondaires.
- [PostgreSQL 17 EXPLAIN](https://www.postgresql.org/docs/17/using-explain.html) : l'analyse réelle a été limitée à une base jetable, et le coût d'un index en écriture reste à suivre.
- [Profilage Node](https://nodejs.org/learn/diagnostics/flame-graphs) : le banc de regroupement identifie une copie quadratique ; un flame graph de charge Gateway réelle reste à produire avant toute proposition de worker thread.
- [Retour d'expérience Xenon, Merlin Fuchs](https://merlinfuchs.com/posts/handling-rate-limits-at-scale) : un proxy peut coordonner plusieurs clients REST, mais ce témoignage d'un gros bot ne prouve pas qu'un proxy soit utile ou rentable pour Veyro maintenant. Son infrastructure et son trafic ne sont pas publics ici au niveau requis pour les reproduire.
