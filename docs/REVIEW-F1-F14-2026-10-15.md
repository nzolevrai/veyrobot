## Correctif de la tranche « assainissement des erreurs et diagnostic » — 2026-10-15

La revue du commit `dd9740dfa0091e87628741128676dab2e404a8a8` a reproduit des fuites dans les messages d'exception : valeur JSON avec clé sensible entre guillemets, affectation avec valeur espacée, JWT brut et URL d'identifiants dont le `@` se trouvait après la limite de troncature. Le filtrage d'un extrait tronqué ne pouvait pas détecter sûrement ces motifs.

Les logs d'exception ne collectent désormais plus `message` ni le texte d'une cause. Ils conservent uniquement le nom d'erreur allowlisté, le code connu, la forme bornée des causes et les champs structurés du contexte (API : requestId, phase, statut, code; bot : événement, source et message d'opération contrôlés par le code). Les causes en chaîne, circulaires, valeurs non Error et getters/proxys atypiques restent traités sans propager d'exception. Le filtrage des textes de contexte bornés reconnaît les clés sensibles JSON/non JSON, les valeurs citées, JWT à trois segments et URLs usuelles; toute entrée de plus de 4096 caractères est remplacée intégralement avant troncature. Ce filtre n'est pas un détecteur universel de secrets arbitraires : la garantie principale vient de l'omission du texte d'exception.

Tests conservés sur les sorties finales des loggers API Pino/Fastify et bot `console.error` reproduisent les quatre formats. Ils ont échoué sur le code antérieur avec le premier canari JSON et passent après correction. Ils vérifient également l'absence de canaris, les diagnostics structurés conservés, les messages bénins de contexte, les causes imbriquées, le budget d'entrée, les valeurs atypiques, les réponses API génériques et la corrélation `requestId`.

Validation locale avec Node 24.21.0 : tests ciblés API/bot (7 réussis); `typecheck`, `lint` et `build` réussis; intégration API sur PostgreSQL 17 jetable après génération Prisma et 13 migrations (OAuth, quotas, routes publiques, panne de validation du grant et lectures de grant bornées). ## Reprise de la tranche « sauvegarde et restauration » — 2026-10-16

Le script refuse désormais une destination Windows préexistante dès qu'une ACE ou identité sort de l'allowlist; il ne réécrit pas son ACL. La politique d'accès est FullControl pour le compte d'exécution, LocalSystem et Administrators local; le propriétaire doit être l'une de ces identités et le compte d'exécution garde une ACE explicite. ACL du dossier, du répertoire temporaire, du verrou `.active`, de l'archive et du sidecar vérifiées. Les chemins reparse sont refusés. Linux utilise le propriétaire de l'UID et modes 0700/0600. Les temporaires locaux et conteneur démarrent dans des répertoires restreints; un verrou exclusif par plage de fichier protège les exécutions actives et le nettoyage d'abandons est limité en âge et en nombre.

La reprise utilise `VEYROBOT_RECOVERY_EPOCH` depuis un coffre indépendant des snapshots. L'API et le bot vérifient le gate avant d'écouter, créer le worker ou publier; l'absence, le décalage et les erreurs DB bloquent le démarrage. La procédure dédiée tourne l'epoch, restaure en cible isolée, puis met dossiers actifs, échéances TEMPBAN et sessions en quarantaine/révocation dans la même transaction qui inscrit le nouveau hash. Elle garantit la procédure supportée, pas la détection d'une restauration arbitraire effectuée sans rotation du secret externe.

La CI sur `b62163bb170f7fa86e3a9f6853df2b5341a36cf1` a révélé que `FileShare.None` seul ne bloquait pas le nettoyage concurrent sous Linux : le test supprimait le répertoire d'un processus encore suspendu. Le verrou utilise désormais `FileStream.Lock(0, 1)` en complément. Le test API de panne de grant simule l'indisponibilité ciblée de `SessionGrant` pendant que le gate reste joignable et rétablit la table dans `finally`.

La CI finale [#62](https://github.com/nzolevrai/veyrobot/actions/runs/38870760733) a réussi sur `28357a440d6bcb152d9dc088af1d720334cd3c2f` : jobs Windows et Ubuntu verts; Node 24.21.0, PostgreSQL 17.11, Redis 7.4.11; migrations, schéma, typecheck, build, lint, suite complète, tests PowerShell Windows/Linux et intégration réelle PostgreSQL 17/Redis 7 réussis. L'intégration a mesuré 2 050,9 ms pour la sauvegarde, 161,6 ms pour la restauration et une archive de 21 989 octets sur données synthétiques. Docker Desktop local était indisponible, donc ces preuves réelles proviennent de la CI. Elles ne valident ni des données de production, ni un RPO/RTO, ni une restauration à l'échelle réelle. Aucun bot connecté à Discord, identifiant réel ou action Discord n'a été utilisé.
